# 写作规范

适用于帖子、界面、文档、报告、邮件、通知和对外文章。审校与动笔时同样遵守。

## 通用文案

- **直接写事实和行动，删掉防御性与免责套话。** 不用「不代表……」「不意味着……」「不是实际……」「不保证……」「仅供参考」等自我保护式补充，也不用「为了严谨」「避免误解」「我不能断言」铺垫。相同限制只在相关位置交代一次，不固定增设免责声明、边界或核验台账。
- **界面提示说明用户能做什么、操作发生了什么。** 不主动强调页面无法核实的后续动作，也不为假设的风险辩解。例如导出提示写「PNG 会开始下载；PDF 会打开打印流程」，不追加「页面无法确认文件是否已保存」。不要把开始下载、打开打印说成文件已保存；发生真实错误或涉及用户必须处理的权限、数据丢失风险时，写清情况和下一步。
- **准确交代已知事实和必要条件。** 区分计划、估算和已完成事项；缺少决定性信息时，说明缺什么、影响哪一步及下一步，能核实的先核实。不得将推测写成事实、将未执行写成已完成，也不得编造数据、来源、验证结果或用户经历。保留必要的安全警告、法定披露和用户要求的风险说明，写明具体风险与处置动作。
- **自然、完整、简洁。** 优先使用日常说法，正式场合保留必要的礼貌与准确性。段落交代主体、动作、结果及必要背景，让句子按因果或时间衔接；自然的口语短句和上下文清楚的省略可以保留。删掉不带新信息的结尾、修饰词、用户未要求的过程日志和自评。
- **不用否定造势。** 避免「不是……而是……」「与其说……不如说……」「并非……只是……」等句式。直接陈述事实；确需比较或纠错时，写清双方事实或正确内容及依据。
- **不用矫饰文风（去 AI 味）。** 避免标题式短句连用、口号式结论、设问揭晓、对仗排比、倒装、拟人与姿态性自评，如「我们相信」「诚实地呈现」「拒绝……」「严谨」「优雅」。不用机械的三个一组；比喻只在降低理解成本时使用，一个概念最多一个。不要文学化升华或抒情收尾，结尾停在一件具体的事上。一句话最多一处破折号，能用其他标点时不用。少用「不仅……更……」「突然」「渐渐」这类填充词和渲染性用词。标题写实，如「河边的旧仓库」，不写「往东开到头」这类修辞。
- **不写元文本。** 不预告或讲解文字本身的组织、取材和读法，例如「先记住九个对应」「下面几张」「接下来」「整理了 16 张」「按……排列」「卡片里同色表示对应」。标题直接写主题事实或结论，图示含义由图和元素标注表达。系列名、页码、出处、署名及平台要求的声明不算元文本。展示页、报告和 README 仍须交代理解主题所需的背景、方法和条件；幻灯片的详细解释可放讲稿或备注。
- **叙述尊重原材料。** 写个人经历时交代事情和真实感受，不替作者赋予成长、身份或人生意义，也不概括国家与文化特质。整体空心的稿子靠加具体细节救（时刻、地名、走了多久、路上车多车少），不靠换词；每段起笔和长短各不相同，不要每段都是「地点＋看点＋知识」的同一套结构。表述要能判断方向，「偶尔有车」改成「车很少」。演讲稿要便于开口，幻灯片要便于一眼读懂。
- **沿用既有的用词约定。** 产品名、站点名、网络与 Wi-Fi 的量词（「同一个 Wi-Fi」「整个酒店的网络」）按项目既有写法处理，不在同一篇里混用。

交付前检查：删除一句话是否影响事实理解或行动；保留的限制是否有具体条件和下一步；事实、估算与状态是否准确，必要警告和披露是否保留。连续两句都不到 15 字时，检查是否刻意制造节奏；不按字数直接判错。

## 中文标点

界面文案、文档和报告里的中文标点用全角：逗号「，」、句号「。」、冒号「：」、分号「；」、叹号「！」、问号「？」、括号「（）」，引号用「」（嵌套用『』），顿号「、」。半角只用于代码与标识符（`gate.Wait()`）、数学式和英文内容自身的标点（`(John Machin, 1706)`），不与汉字直接相邻；数字与单位间的空格、`26.0°C`、`09/03 20:00` 等数字格式照旧。

用测试检查渲染文本：剥掉 style、script 和标签，还原 HTML 实体，断言不匹配 `\p{Han}[,;:()!?"]|[,;:()!?"]\p{Han}`；JS 用 `\p{Script=Han}` 和 `u` 标志，Go 用 `\p{Han}`。后端显示到页面的字符串用 go/parser 扫字符串字面量，JSON 语法双引号不算，正则去掉 `"`。

自动转换时也检查 JSX 表达式之间的文本（如 `按键:{x}`、`{a}({b})`）及运行期拼接的标点（如 `reason + ":" + x`）；括号成对转换。

## 小红书

写小红书标题、正文、图卡或配图说明时，同时遵守通用规范。

- **标题**：中英文间留空格，完整标题不超过 20 字符；汉字、字母、数字、空格和标点逐个计数，先排空格再计数。尽量不用计数口径不稳定的 emoji，用脚本核对最终标题和中英文间距。
- **内容**：从真实场景和遇到的问题讲个人使用 AI 的经历，交代提供的信息、AI 做了什么、哪里不对以及如何处理。可使用真实的小失误、意外和前后差异，不虚构经历、心情、对话、数字或效果；改写的任务要求标为示例。
- **可读性**：用连贯句子给不熟悉项目的读者交代场景，再引入必要术语。按用途和具体事件组织工具与基础设施，避免项目目录、技术栈堆砌、功能广告和人生哲学；无依据时不用「零基础」「全自动」「替代团队」等效果宣称。
- **多图叙事**：按指定张数安排封面、场景、过程、问题与方法，每张图有明确作用并与前后衔接。正文提供完整线索，图卡补充细节，避免逐页重复或拆碎内容凑数。亲眼看到的东西直接写成分享，背景知识当普通一句话带出，不贴「冷知识」「干货」这类标签；不写「注意事项」式的提醒口吻，经验写成自己当时的安排。不拿别处作对照来抬高（「没去大理」「一般人不去」），读者不认识的地名补一句它在哪个市旁边。
- **盘点范围**：以要求的终态、系统及用途为准；要求总表时对照正文和图卡查漏，要求不写磨合时不单列排错页。共享数据、固定口径和统一登录等按实际功能表述，已有专题可留入口。
- **成本**：使用当前账单和调用记录，明确期间、币种、月费折算、暂估和未计入项；开发订阅与其他项目费用分开，不能把共享 API 账户余额差全部算作服务运行费。
- **交付前**：核对标题长度与空格、指定图数、正文与图卡一致性、文字溢出和效果宣称。第一人称稿件只写有证据的亲历；技术核对和完整基础设施清单可放附件。
